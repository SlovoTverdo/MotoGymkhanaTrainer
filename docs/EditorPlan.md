# Editor Implementation Plan

## 1. Назначение

Редактор создаётся для устранения необходимости вручную писать JSON и рассчитывать координаты геометрии трассы.

Полный workflow:

```text
Exercise Editor
        ↓
Exercise Definition JSON
        ↓
Track Editor
        ↓
Exported Track JSON
        ↓
Viewer
```

Редакторские режимы реализуются отдельными сценами:

```text
Exercise Editor
Track Editor
```

Актуальный план Track Editor описан отдельно:

```text
docs/TrackEditorPlan.md
```

---

# 2. Основной принцип реализации

Редактор должен быть двумерным и работать с видом сверху.

Причины:

* удобное позиционирование объектов;
* точная работа с сеткой;
* наглядное отображение расстояний;
* простое редактирование trajectory;
* отсутствие проблем выбора объектов в перспективе;
* удобное редактирование Bezier handles.

Трёхмерный preview не входит в первую версию.

---

# 3. Размещение внутри проекта

Viewer и Editor могут находиться в одном Godot-проекте, но должны быть разделены по сценам и ответственности.

Рекомендуемая структура:

```text
scenes/
├── viewer/
│   └── Viewer.tscn
└── editor/
    └── ExerciseEditor.tscn
```

Рекомендуемая структура scripts:

```text
scripts/
├── domain/
├── serialization/
├── common/
├── rendering/
├── viewer/
└── editor/
```

Не требуется немедленно перестраивать существующую структуру каталогов, если она уже логична.

Не выполнять массовое перемещение рабочих файлов только ради соответствия примеру.

---

# 4. Разделение моделей

Необходимо различать:

```text
ExportedTrackData
ExerciseDefinitionData
```

Корневые DTO должны быть разными.

Общие вложенные модели могут переиспользоваться там, где их семантика действительно совпадает:

* точки;
* cones;
* markings;
* trajectory;
* trajectory segments.

Не создавать универсальный `DocumentData`, содержащий поля всех возможных форматов.

---

# 5. Editor Iteration 1 — базовый редактор конусов

## Цель

Получить рабочий 2D-инструмент, позволяющий создать, сохранить и повторно открыть Exercise Definition с конусами.

Trajectory в этой итерации может создаваться автоматически как минимальная допустимая прямая между entry и exit либо оставаться временной фиксированной заготовкой.

Полноценное редактирование trajectory относится к Iteration 2.

---

## 5.1. Сцена редактора

Создать отдельную сцену:

```text
ExerciseEditor.tscn
```

Рекомендуемая компоновка:

```text
┌─────────────────────────────────────────────┐
│ Toolbar                                     │
├──────────────┬──────────────────────────────┤
│ Tools        │                              │
│              │                              │
│ Select       │       2D workspace           │
│ Add Cone     │       top view               │
│ Delete       │       meter grid             │
│              │                              │
├──────────────┼──────────────────────────────┤
│ Document     │ Selected object properties   │
└──────────────┴──────────────────────────────┘
```

Точный визуальный дизайн не фиксируется.

Приоритет:

* ясность;
* предсказуемость;
* функциональность;
* минимальное количество скрытых режимов.

---

## 5.2. Рабочая область

Рабочая область должна:

* отображать bounds упражнения;
* отображать grid;
* поддерживать pan;
* поддерживать zoom;
* переводить координаты курсора в локальные метры;
* отображать origin;
* отображать оси или их обозначения.

Базовая grid:

```text
1 × 1 метр
```

Рекомендуется:

* тонкая линия каждый метр;
* более заметная линия каждые 5 метров;
* отображение origin;
* возможность отключить snap.

---

## 5.3. Camera / Canvas navigation

Предлагаемое управление:

```text
колесо мыши     — zoom
средняя кнопка  — pan
```

Допустимы другие решения, если они не конфликтуют с редактированием объектов.

Zoom должен происходить относительно позиции курсора или центра viewport предсказуемым образом.

Редактор должен сохранять стабильное соответствие:

```text
world/editor units = meters
```

---

## 5.4. Новый документ

Команда `New Exercise` должна позволять указать:

* exercise id;
* name;
* bounds width;
* bounds length.

Начальные значения могут быть:

```text
width  = 10 m
length = 10 m
```

После создания:

* origin находится в центре;
* документ считается изменённым;
* рабочая область адаптируется под bounds.

---

## 5.5. Добавление конуса

Инструмент:

```text
Add Cone
```

Поведение:

1. пользователь выбирает инструмент;
2. кликает по рабочей области;
3. создаётся конус в соответствующих локальных координатах;
4. новому конусу назначается уникальный id;
5. объект становится выделенным.

Если после snap в выбранных координатах уже существует конус, новый объект не
создаётся: существующий конус становится активным.

Начальные свойства:

```text
type  = standard
color = red
```

В свойствах также доступно `color = none`: оно сохраняется в JSON и означает
отсутствие дополнительного цветного навершия в Viewer.

---

## 5.6. Выбор конуса

Инструмент:

```text
Select
```

Клик по конусу:

* выделяет его;
* показывает визуальную рамку или маркер;
* отображает свойства объекта.

Клик по пустому месту:

* снимает выделение.

При перекрытии нескольких объектов допускается выбор верхнего объекта.

Сложный cycling selection в первой версии не требуется.

---

## 5.7. Перемещение конуса

Выделенный конус можно перемещать drag-and-drop.

При включённом snap позиция округляется к шагу сетки.

Рекомендуемый начальный snap:

```text
0.25 m
```

Допустимо использовать:

```text
0.5 m
```

если это значительно проще.

Позицию также можно редактировать численно:

```text
X
Y
```

Ввод чисел должен обновлять объект на canvas.

Перемещение объекта на canvas должно обновлять числовые поля.

---

## 5.8. Свойства конуса

Минимальная панель:

```text
Id
Position X
Position Y
Color
Type
```

`id` можно показывать только для чтения.

Не требуется реализовывать ручное изменение id в первой версии.

---

## 5.9. Удаление

Выделенный конус удаляется:

* клавишей Delete;
* кнопкой Delete.

После удаления выделение очищается.

---

## 5.10. Bounds

Bounds должны быть видимыми.

Редактор должен позволить изменить:

```text
width
length
```

При изменении bounds существующие объекты не должны автоматически масштабироваться.

Если объект оказывается за пределами bounds:

* он не удаляется;
* его координаты не меняются;
* редактор показывает предупреждение или визуальный индикатор.

---

## 5.11. EntryPoint и ExitPoint в Iteration 1

Чтобы файл Exercise Definition соответствовал контракту, Iteration 1 должна иметь entry и exit.

Минимальный вариант:

* показывать два специальных маркера;
* позволять перемещать их drag-and-drop;
* позволять редактировать координаты численно.

Временная trajectory может автоматически состоять из одного `polyline`:

```text
entryPoint → exitPoint
```

Это временное поведение должно быть явно локализовано и заменено в Iteration 2.

Не создавать сложную архитектуру ради временной прямой trajectory.

---

## 5.12. Сохранение

Команда:

```text
Save Exercise
```

должна сохранять JSON согласно:

```text
docs/ExerciseFormat.md
```

Требования:

* UTF-8;
* читаемое форматирование;
* `formatVersion = 1`;
* стабильные id существующих объектов;
* отсутствие runtime/editor-only данных;
* отсутствие экранных координат;
* отсутствие масштаба viewport и положения pan.

---

## 5.13. Загрузка

Команда:

```text
Open Exercise
```

должна:

1. открыть file dialog;
2. прочитать JSON;
3. десериализовать DTO;
4. проверить `formatVersion`;
5. выполнить базовую валидацию;
6. только после успешной проверки заменить текущий документ.

При ошибке:

* текущий документ не уничтожается;
* отображается понятное сообщение;
* подробности записываются в лог.

---

## 5.14. Unsaved changes

Перед:

* `New`;
* `Open`;
* закрытием редактора;

при наличии несохранённых изменений следует предупредить пользователя.

Для первой итерации допустим простой диалог:

```text
Save
Discard
Cancel
```

Если корректная обработка закрытия окна существенно усложняет Iteration 1, её можно перенести в отдельную малую итерацию, но `New` и `Open` не должны молча уничтожать изменения.

---

## 5.15. Definition of Done — Editor Iteration 1

* Отдельная Exercise Editor scene запускается.
* Можно создать новый документ.
* Видны bounds и meter grid.
* Работают pan и zoom.
* Можно добавить конус.
* Можно выделить конус.
* Можно переместить конус.
* Работает snap.
* Можно изменить цвет.
* Можно удалить конус.
* EntryPoint и ExitPoint редактируются.
* Файл сохраняется как Exercise Definition JSON.
* Сохранённый файл повторно открывается.
* Ошибочный JSON не уничтожает текущий документ.
* Существующий Viewer продолжает работать.
* Нет compile/runtime errors.
* Код подробно прокомментирован.

---

# 6. Editor Iteration 2 — Polyline trajectory

## Цель

Добавить удобное визуальное редактирование trajectory как polyline.

---

## 6.1. Инструмент trajectory

Добавить режим:

```text
Edit Trajectory
```

В нём пользователь может:

* создать первую точку;
* добавлять следующие точки;
* завершить построение;
* выделять существующие точки;
* перемещать точки;
* удалять точки;
* вставлять точку между соседними.

При построении новой trajectory каждый участок по умолчанию создаётся как
`cubicBezier`. Первый участок начинается прямым spline. Для каждого следующего
участка `control1` зеркалит предыдущий `control2` относительно общего anchor,
что обеспечивает касательное сопряжение. Команда преобразования выбранного
участка обратно в line/polyline сохраняется.

---

## 6.2. Представление

Trajectory должна отображаться:

* линией;
* маркерами anchor points;
* указателями направления;
* отдельным стилем выделенного segment или point.

Первая точка автоматически является:

```text
entryPoint
```

Последняя точка автоматически является:

```text
exitPoint
```

После Iteration 2 entry/exit не должны редактироваться независимо от концов trajectory.

Их свойства в UI могут быть read-only или редактировать непосредственно соответствующие конечные точки.

---

## 6.3. Минимальное число точек

Polyline segment должен содержать минимум две точки.

Не разрешать сохранение валидного документа с одной точкой trajectory.

При попытке удалить точку, если останется менее двух:

* операция блокируется;
* либо документ отмечается как невалидный до исправления.

Предпочтительнее блокировать удаление в первой версии.

---

## 6.4. Непрерывность

В Iteration 2 trajectory может состоять из одного `polyline` segment.

Это сознательное ограничение.

Не создавать систему нескольких segments до начала Iteration 3.

---

## 6.5. Definition of Done — Editor Iteration 2

* Можно визуально создать polyline.
* Можно перемещать её точки.
* Можно вставлять и удалять внутренние точки.
* EntryPoint всегда равен первой точке.
* ExitPoint всегда равен последней точке.
* Сохранение соответствует ExerciseFormat.
* Viewer и Track DTO не повреждены.
* Старые Exercise Definition корректно загружаются, если соответствуют версии 1.

---

# 7. Editor Iteration 3 — CubicBezier

## Цель

Добавить визуальное создание и редактирование кривых Безье без ручного ввода координат.

---

## 7.1. Преобразование segment

Предлагаемая операция:

```text
Convert selected segment to Cubic Bezier
```

Точный UX может быть уточнён после Iteration 2.

Пользователь не должен редактировать `control1` и `control2` только числовыми полями.

---

## 7.2. Handles

Для выбранной кривой отображаются:

* start anchor;
* end anchor;
* control1 handle;
* control2 handle;
* вспомогательные линии anchor-to-handle.

Перетаскивание handle изменяет соответствующую управляющую точку.

---

## 7.3. Rendering

Кривая дискретизируется для canvas rendering.

DTO и JSON сохраняют:

```text
start
control1
control2
end
```

Не заменять Bezier в сохраняемом файле массивом вычисленных точек.

---

## 7.4. Несколько segments

Iteration 3 вводит полноценный:

```text
trajectory.segments[]
```

Редактор должен поддерживать последовательность `polyline` и `cubicBezier`.

Конец предыдущего segment и начало следующего должны использовать общий anchor либо оставаться синхронизированными.

Не допускать появления разрыва из-за перемещения только одной копии общей точки.

---

## 7.5. Definition of Done — Editor Iteration 3

* Можно создать или получить `cubicBezier`.
* Control handles редактируются мышью.
* Кривая визуально обновляется.
* Сохраняются исходные Bezier control points.
* Поддерживается непрерывная последовательность segments.
* Entry/Exit вычисляются по первому и последнему segment.
* Файл проходит валидацию ExerciseFormat.

---

# 8. Editor Iteration 4 — Markings

## Цель

Добавить дополнительную цветовую разметку.

Первоначальные типы:

```text
line
polyline
```

Свойства:

* points;
* color;
* widthMeters.

Не реализовывать дуги, полигоны и стрелки, пока они не потребуются для реальных элементов.

---

# 9. Track Editor

Track Editor является отдельным редакторским режимом и отдельной сценой.

Его формат проекта, итерации и ограничения описаны в:

```text
docs/TrackProjectFormat.md
docs/TrackEditorPlan.md
```

Exercise Editor не встраивается в Track Editor: Track Editor использует сохранённые
Exercise Definition из `res://exercises/` как внешнюю библиотеку.

---

# 10. Что нельзя смешивать с первой итерацией

В Exercise Editor Iteration 1 не добавлять:

* размещение ExerciseInstance на площадке;
* rotation и scale экземпляров;
* автоматические переходные spline;
* cubicBezier editing;
* markings editor;
* checkpoints;
* 3D preview;
* окружение;
* Viewer refactoring без необходимости;
* Web export;
* GitHub Pages;
* undo/redo framework;
* plugin architecture;
* event bus;
* dependency injection framework.

Undo/redo действительно понадобится редактору, но его следует добавить отдельной итерацией после проверки базового взаимодействия.

---

# 11. Критерий архитектурной простоты

Редактор должен иметь явную модель текущего документа:

```text
ExerciseEditorDocument
```

Она содержит редактируемые данные упражнения и состояние dirty/validation.

Экранное состояние должно храниться отдельно:

```text
zoom
pan
selected object
active tool
snap settings
```

Экранное состояние не сериализуется в Exercise Definition JSON.

Не создавать несколько конкурирующих копий модели документа в UI, canvas и serializer.

Должен существовать один источник редактируемых данных.

---

# 12. Проверка результата

После каждой итерации Codex должен:

1. собрать проект;
2. запустить соответствующую scene;
3. проверить основные действия;
4. сохранить JSON;
5. повторно открыть сохранённый JSON;
6. проверить ошибки Godot и .NET;
7. убедиться, что Viewer по-прежнему запускается.

Если MCP не позволяет автоматизировать конкретное UI-действие, Codex должен:

* выполнить доступные проверки;
* явно перечислить ручные проверки для пользователя;
* не заявлять, что непроверенное действие успешно работает.

# Editor Iteration 4 — Exercise Library and Markings

## Цель

Завершить базовую функциональность Exercise Editor:

1. организовать Exercise Definition как библиотеку внутри проекта;
2. поддержать пользовательские подпапки;
3. добавить полноценное создание и редактирование markings;
4. поддержать свойства:

   * color;
   * width;
   * style;
   * visibleInViewer.

После завершения этой итерации Exercise Editor считается базово функционально завершённым.

Отдельные arc/circle primitives пока не реализуются.

---

# 1. Exercise Library

Корневой каталог:

```text
exercises/
```

Он является библиотекой Exercise Definition.

Пример:

```text
exercises/
├─ basic/
├─ slalom/
├─ circles/
└─ custom/
```

Подпапки не имеют фиксированной семантики.

Пользователь может создавать произвольную вложенную структуру.

---

## 1.1. Library root

Exercise Editor должен считать:

```text
res://exercises/
```

корнем библиотеки.

При первом запуске, если каталог отсутствует, его следует создать.

Не создавать обязательный набор категорий автоматически.

Пустой `exercises/` является валидным состоянием.

---

## 1.2. Library browser

Exercise Editor должен отображать дерево:

```text
exercises/
├─ folder
│  ├─ subfolder
│  └─ exercise.json
└─ exercise.json
```

Минимальные операции:

* выбрать папку;
* открыть Exercise Definition;
* создать подпапку;
* сохранить текущий Exercise в выбранную папку;
* обновить дерево.

Удаление и переименование папок можно отложить, чтобы избежать рискованных файловых операций.

---

## 1.3. Create Folder

Пользователь может создать подпапку внутри выбранной папки.

Требования:

* имя не пустое;
* запрещены недопустимые для файловой системы символы;
* нельзя выйти за пределы `exercises/`;
* существующая папка не перезаписывается;
* ошибка отображается пользователю.

---

## 1.4. Save Exercise

Для нового документа:

```text
Save
    ↓
выбор папки в Exercise Library
    ↓
имя файла
```

Рекомендуемое имя по умолчанию строится из:

```text
exercise.id
```

например:

```text
slalom-5.json
```

Editor не должен автоматически перемещать существующий файл при изменении `exercise.id`.

`Save As` может сохранять копию в другой папке.

---

## 1.5. Security boundary

Все операции Exercise Library должны оставаться внутри:

```text
res://exercises/
```

Нельзя позволять относительным путям вида:

```text
../../
```

# 2. Marking Editor

Добавить инструмент:

```text
Add Marking
```

Первоначально поддерживаются:

```text
line
polyline
```

---

## 2.1. Создание line

Пользователь:

1. выбирает `Add Line`;
2. задаёт первую точку;
3. задаёт вторую точку;
4. marking создаётся и становится выбранным.

---

## 2.2. Создание polyline

Пользователь:

1. выбирает `Add Polyline`;
2. кликами добавляет points;
3. завершает построение понятным действием.

Минимум:

```text
2 points
```

---

## 2.3. Редактирование points

Для выбранного marking:

* отображаются anchor points;
* точки можно выбирать;
* перемещать drag-and-drop;
* редактировать X/Y численно.

Для polyline желательно также поддержать:

* вставку точки;
* удаление внутренней точки.

Не допускать менее двух points.

---

## 2.4. Marking properties

Панель свойств выбранного marking:

```text
Id
Type
Color
Width
Style
Visible in Viewer
```

### Color

Использовать color picker.

Сохранять канонически:

```text
#RRGGBB
```

### Width

Редактируется в метрах.

Пример:

```text
0.05
0.10
0.15
```

Значение должно быть положительным.

### Style

Dropdown:

```text
Solid
Dashed
Dotted
```

Сериализация:

```text
solid
dashed
dotted
```

### Visible in Viewer

Checkbox:

```text
Visible in Viewer
```

По умолчанию:

```text
true
```

---

## 2.5. Editor rendering

Markings должны отображаться в Exercise Editor с учётом:

* color;
* width;
* style.

`visibleInViewer = false` не скрывает marking в Editor.

Такой marking должен визуально отличаться, например уменьшенной opacity.

---

# 3. Viewer rendering

Viewer должен поддерживать:

```text
solid
dashed
dotted
```

и:

```text
visibleInViewer
```

Неизвестный style:

```text
warning
+
fallback solid
```

Невидимый marking:

```text
не render
```

---

# 4. Format migration

Exercise Definition:

```text
formatVersion 1 → 2
```

При загрузке версии 1:

```text
style = solid
visibleInViewer = true
```

для всех существующих markings.

Допускается автоматическая in-memory migration.

Файл становится version 2 только после явного Save пользователем.

Exported Track:

```text
formatVersion 2 → 3
```

Для version 2:

```text
style = solid
visibleInViewer = true
```

при необходимости backward compatibility.

# 6. Definition of Done

## Exercise Library

* существует `res://exercises/`;
* Editor отображает дерево;
* можно создать подпапку;
* можно сохранить Exercise в выбранную подпапку;
* можно открыть Exercise из дерева;
* вложенные подпапки работают;
* невозможно выйти за пределы library root.

## Markings

* можно создать line;
* можно создать polyline;
* можно выбирать и перемещать points;
* можно задать arbitrary RGB color;
* можно задать widthMeters;
* поддерживаются solid/dashed/dotted;
* работает visibleInViewer;
* сохранение и повторная загрузка сохраняют все свойства.

## Viewer

* visible markings отображаются;
* hidden markings не отображаются;
* solid/dashed/dotted корректно различаются;
* старые Track JSON не ломаются согласно выбранной migration strategy.

## Regression

* cones работают;
* polyline trajectory работает;
* cubicBezier trajectory работает;
* Exercise Save/Open работает;
* Viewer работает;
* нет compile/runtime errors.
